# Survey Flow wiring — Prolific Part 2 (BFI-2 + RPS)

Precise enough for a human to build the actual Survey Flow in the Qualtrics
UI on top of `output/BFI-2_Full_RPS.qsf` (generated by
`.claude/skills/bfi2-qsf-splitter/add_rps.py`), or to use the generated
starting point (`.claude/skills/bfi2-qsf-splitter/wire_qualtrics_flow.py`
-> `output/BFI-2_Full_RPS_Wired.qsf`) and finish the still-manual pieces.
Companion to `ase2-ai-mode`'s own Qualtrics integration docs, which this
follows for the parts common to every part-2-style survey (the
`POST /api/qualtrics/verdict` contract, `"part": "personality"`, the
`pass`/`review` redirect, the error fallback) — but the request contract
this doc describes below is a real change from that generic spec, so
`ase2-ai-mode`'s side needs updating too (see §6, the handoff section).

## 1. Why this design: JavaScript was abandoned

**Historical note, so this isn't reinvented:** the original design
computed `drip_score`/`bfi_answered` client-side, in a hidden question's
custom JavaScript (`Qualtrics.SurveyEngine.addOnReady(...)`,
`setJSEmbeddedData()`), then had the Web Service element send the
pre-computed values. This looked simpler — smaller Web Service body, no
server-side DRIP calculator — and was built, tested with `qsf_lint.py`,
and imported successfully.

It doesn't work. Extensive live testing (real completed-response exports,
both Qualtrics Preview and a published "Test Survey" link, both Classic
and New Survey Taking Experience) established that **Question JavaScript
never executes at all** in the target Qualtrics account — not a syntax
problem, not a piped-text problem: even the most trivial possible script
(`setJSEmbeddedData("__js_debug_dump", "JS_RAN_OK")`, no piped text, no
dependencies) never wrote its value, in every test, including on a page
confirmed to render correctly. The account's own Qualtrics admin team
couldn't diagnose it further. **Don't reintroduce a JS-based design for
this gate without first confirming Question JavaScript actually executes
in the target account** (a definitive, cheap test: a visible DOM mutation
like `document.body.style.backgroundColor = "red"` in `addOnReady`,
checked in a real Preview/Test Survey run, not just the "Add JavaScript"
panel accepting the code). "Switch Survey Taking Experience" is not a
fix worth retrying blind: Classic and New Survey Taking Experience were
both tested (the survey was switched to New mid-session — confirmed by a
completely different response-page DOM structure — and the JS still
never ran under either), and Qualtrics's own docs state custom JavaScript
is supported under the New experience. Whatever's blocking it is
account/brand-level, not a per-survey display setting.

The current design instead sends every input the two signals need — all
60 raw BFI-2 item answers, plus the attention-check score — directly in
the Web Service request, and computes `drip_score`/`bfi_answered`
**server-side**, in `ase2-ai-mode`. Two Qualtrics mechanisms make this
possible without any custom code, both confirmed live this session via
real completed-response exports (not just the Web Service element's own
"Test" button, which never substitutes piped text — it only echoes the
literal `${...}` template, a dead end for validating any of this):

- `${q://QID2/SelectedAnswerRecode/<ChoiceID>}` — a Matrix row's recoded
  numeric answer, piped directly as a Web Service Body Parameter value
  (not inside JS). Note the exact name: `SelectedAnswerRecode` (singular
  "Answer"), not `SelectedChoicesRecode` — multiple Qualtrics community
  threads report the latter, and per-row Matrix piped text generally, as
  unreliable *inside JavaScript*; `SelectedAnswerRecode` used directly as
  a Body Parameter value was confirmed correct across two different real
  responses in this repo's own testing.
- `${gr://SC_<category-id>/Score}` — native Qualtrics Scoring (the same
  `GradingData`/`SCO` mechanism this repo already uses for domain/facet/
  RPS totals), piped the same way. Used here for the attention-check
  score, confirmed to vary correctly per response (including a failed
  attention check yielding `0`).

## 2. Survey Flow structure

```
Participant lands (from ase2-ai-mode's Part-1 pass -> Part-2 Prolific link)
  -> Embedded Data: capture prolific_pid/study_id/session_id from URL;
     fail-closed defaults (verdict=review, a fallback next_url, blank
     signal fields) -- what's left in place if the Web Service below
     never runs, times out, or errors
  -> Content block: 60 BFI-2 items + 7 RPS items + 1 attention-check row
     (one page, per this repo's existing single-page convention)
  -> Web Service: POST /api/qualtrics/verdict (ase2-ai-mode), synchronous,
     sending all 60 raw item answers + attention-check score + reCAPTCHA
     score; server computes drip_score/bfi_answered and returns a verdict
  -> pass: redirect to next_url (Part 3)
     review: redirect to next_url (review completion code)
```

No JavaScript question, no `Branch` element for the attention check (the
native scoring category's value is sent directly, computed server-side
into a boolean), no `EmbeddedData` copy step. This is a smaller Survey
Flow than the original design, not a bigger one.

### Generated vs. still-manual

`wire_qualtrics_flow.py` generates the initial `EmbeddedData` defaults,
the full `WebService` element (all 68 body fields, `ResponseMap`,
placeholder URL), and switches the survey to Qualtrics's "New Survey
Taking Experience" skin (`SO.SkinType`/`Skin`/`SkinLibrary`) — confirmed
**safe** to inject on import via live bisection (unlike Bot Detection,
below). `Skin.brandingId` is RMIT-account-specific, not a generic BFI-2
default — acceptable here since this generator's whole output is already
RMIT/this-study-specific (Prolific fields, an `ase2-ai-mode` endpoint);
the plain `BFI-2_Full`/`Short`/`ExtraShort` forms this script doesn't
touch stay Colby-neutral and portable.

It does **not** generate, and these remain manual UI steps after import:

- Bot Detection (`RecaptchaV3`/`IncludeSecurityFields` on the `SO`
  element) — **tried and reverted.** Those exact keys/values were
  confirmed present in donor exports of surveys with Bot Detection
  enabled through the UI, but injecting them via a plain JSON patch on a
  freshly-imported `.qsf` broke the import outright ("Something went
  wrong and the project wasn't created", live-tested, reproduced,
  isolated by bisection). Bisected further, one field at a time:
  `RecaptchaV3: true` alone (with `IncludeSecurityFields` left `false`)
  **fails**; `IncludeSecurityFields: true` alone (with `RecaptchaV3` left
  `false`) **also fails** — so this isn't a pairing/combination quirk,
  each field independently breaks import. Best-supported explanation
  found via research (Qualtrics's own docs don't cover this QSF behavior
  either way): the importer applies feature-level validation beyond JSON
  parsing, and Bot Detection specifically isn't an accepted state to
  create *through* a QSF import, regardless of whether it's provisioned
  in the account (this account clearly has the feature — it works fine
  toggled on manually, post-import). Presence in an *export* isn't proof
  a value is safe to *inject* on *import* — a distinction this project's
  been burned by before. Enable Bot Detection manually in the Qualtrics
  UI (Survey Options > Security) after import instead. If API access
  ever becomes available, `PUT /survey-definitions/{surveyId}/options`
  (confirmed to exist and to accept undocumented option fields per
  Qualtrics Community reports) is the architecturally correct
  post-import alternative to try — `GET` an already-enabled survey's
  options first and reuse its exact returned shape, don't construct one
  from `.qsf` internals.
- The verdict `Branch` (routing on `${e://Field/verdict}`) and the
  redirect/`EndSurvey` nodes — needs a real donor `.qsf` export containing
  these element types before their exact shape can be trusted (same
  reasoning that kept the original `WebService` element manual until a
  donor export existed for *that* — see git history on this file).
- A custom auth-secret header (`x-qualtrics-secret` or similar) on the
  `WebService` element — only an empty `Headers: []` is confirmed against
  a real export; the shape of a populated `Headers` entry isn't. Add it
  in the Qualtrics UI after import.
- Pointing the `URL` field at the real server (the committed file uses
  `https://example.invalid/api/qualtrics/verdict`).

**The committed `output/BFI-2_Full_RPS_Wired.qsf` is not deployable as
imported** — its `SurveyName` says so explicitly
(`[quality Web Service generated; auth and routing manual]`).

## 3. Request contract

Flat JSON body, 68 fields, every value a plain string (no `parameterType`
on any Body Parameter — this matters: an unanswered Matrix row resolves to
`""`, and a `Number`/`JSON` parameterType could coerce that away, losing
the answered/unanswered distinction `bfi_answered` needs):

| Field | Value | Notes |
|---|---|---|
| `contract_version` | `"personality-raw-bfi-v1"` | literal |
| `part` | `"personality"` | literal |
| `drip_spec_sha256` | `canonical_spec_sha256()` of the 15-pair table | see §5 |
| `prolific_pid`, `prolific_study_id`, `prolific_session_id` | piped from the Embedded Data defaults | |
| `attention_check_score` | `${gr://SC_.../Score}` | native scoring, `"1"` or `"0"` |
| `recaptcha_score` | `${e://Field/Q_RecaptchaScore}` | Qualtrics's built-in Bot Detection score |
| `bfi_01` .. `bfi_60` | `${q://QID2/SelectedAnswerRecode/<ChoiceID>}` | one per BFI-2 item, `""` if unanswered |

Not sent: RPS's own 7 answers (not needed for either signal; the 9-point
`SelectedAnswerRecode` behavior is unconfirmed and unused), a
`duration_seconds` field (no confirmed non-JS source for a real elapsed-
time measurement — deferred; don't send a fake `0`), any nested object
(`extra_signals` or similar — the body is deliberately flat, simpler to
generate/inspect/debug than nesting).

`Q_RecaptchaScore` caveat: Bot Detection is a manual, easy-to-forget
post-import UI step (see §2's "Generated vs. still-manual") — a survey
that never had it enabled sends `recaptcha_score = ""` on every response,
always. Treat blank as "no signal," not "failed check" (see §6's verdict
logic) — don't force review purely because it's blank. Qualtrics's own
fail-open default if reCAPTCHA fails to *load* on an *enabled* survey is
`1` — that is **not** proof of a verified human either, just Qualtrics's
own can't-tell value.

### Response and `ResponseMap`

`ase2-ai-mode` should return:

```json
{
  "verdict": "pass",
  "next_url": "https://...",
  "completion_code": "...",
  "quality_signals": {
    "drip_score": 8,
    "bfi_answered": 60,
    "attention_checks_passed": true,
    "recaptcha_score": 1.0
  }
}
```

Generated `ResponseMap` (not required for the gate's own decision — that's
the `verdict`/`next_url`/`completion_code` fields, which the eventual
manual `Branch`/redirect nodes read directly — but valuable for auditing
completed-response exports, e.g. comparing the server's `drip_score`
against `response_verification/verify_responses.py`'s offline scoring):

```json
[
  {"key": "verdict", "value": "verdict"},
  {"key": "next_url", "value": "next_url"},
  {"key": "completion_code", "value": "completion_code"},
  {"key": "quality_signals.drip_score", "value": "drip_score"},
  {"key": "quality_signals.bfi_answered", "value": "bfi_answered"},
  {"key": "quality_signals.attention_checks_passed", "value": "attention_checks_passed"},
  {"key": "quality_signals.recaptcha_score", "value": "gate_recaptcha_score"}
]
```

Orientation: `key` is the JSON path to extract from the response, `value`
is the destination embedded-data field name — confirmed live this
session (the reverse orientation silently produces blank fields: the
export column gets named after `value`, but its content stays empty
because `key` isn't a real path in the response body).

(`gate_recaptcha_score`, not `recaptcha_score`, to avoid colliding with
Qualtrics's own `Q_RecaptchaScore` field in exports.)

## 4. Generated `.qsf` shape (confirmed, not guessed)

Captured from a real donor export this session — `EditBodyParams` is a
flat array of `{key, value}` (no `parameterType` for plain strings), `Body`
mirrors the same data as a real JSON object:

```json
{
  "Type": "WebService",
  "FlowID": "FL_4",
  "URL": "https://example.invalid/api/qualtrics/verdict",
  "Method": "POST",
  "RequestParams": [],
  "EditBodyParams": [
    {"key": "contract_version", "value": "personality-raw-bfi-v1"},
    {"key": "bfi_01", "value": "${q://QID2/SelectedAnswerRecode/1}"}
  ],
  "Body": {"contract_version": "personality-raw-bfi-v1", "bfi_01": "${q://QID2/SelectedAnswerRecode/1}"},
  "ContentType": "application/json",
  "Headers": [],
  "ResponseMap": [...],
  "FireAndForget": false,
  "SchemaVersion": 0,
  "StringifyValues": true
}
```

`bfi_01`..`bfi_60` are built from `QID2`'s **real Choice IDs**, read from
the input `.qsf` (`wire_qualtrics_flow.py`'s `find_bfi_question()`) — never
a blind `range(1, 61)`. If a future edit changes `QID2`'s Choice ID scheme
(gappy, non-numeric, reordered), the generator rejects the input rather
than silently generating a wrong or incomplete body.

## 5. DRIP pair-table sync (`drip_spec.py`)

`drip_spec.py` (not `gen_drip_js.py`, deleted — it only ever generated the
now-abandoned JS) owns loading/validating/hashing the 15-pair spec from
`response_verification/drip_item_pairs.tsv`. `canonical_spec_sha256()`
hashes a **canonical, exactly-specified** serialization: compact JSON
array, TSV row order, each row `{item1, item2, reverse1, reverse2, domain,
facet}` in exactly that key order, real JSON integers/booleans (not
strings), `separators=(",", ":")`, `ensure_ascii=True`. This hash rides in
every Web Service request as `drip_spec_sha256`.

**`ase2-ai-mode` must vendor an exact copy of `drip_item_pairs.tsv`** and
reproduce the identical canonical serialization to compute the same hash
— see §6. A mismatch means the two repos have drifted (someone edited one
pair table but not the other) and should fail closed: a tracked `review`
verdict with reason `drip_spec_mismatch`, never a silently-wrong
computation against the wrong table.

## 6. `ase2-ai-mode` handoff

This repo's changes are done; `ase2-ai-mode` needs a corresponding update,
not built in this session (that repo isn't open here). Precise spec:

**Request schema**, for `part="personality"` and
`contract_version="personality-raw-bfi-v1"`:
- Require exactly `bfi_01`..`bfi_60` as strings. `""` means unanswered;
  `"1"`-`"5"` are valid answers. Anything else in a `bfi_NN` field is a
  malformed response value (not a request-level problem) — treat as
  fail-closed `review`, not a 422.
- Require `attention_check_score` (string `"1"`/`"0"`; blank/unexpected ->
  review), `recaptcha_score` (string, **optional signal, not a required
  one** — see below), `drip_spec_sha256` (compare against the vendored
  table's own hash; mismatch -> review with reason `drip_spec_mismatch`).
- `recaptcha_score` handling: Bot Detection is a **manual, easy-to-forget
  post-import UI step** (`wire_qualtrics_flow.py` can't generate it —
  confirmed live that injecting `RecaptchaV3`/`IncludeSecurityFields`
  into the `.qsf` breaks import outright, bisected one field at a time,
  both individually fail). If it was never enabled on a given survey,
  `${e://Field/Q_RecaptchaScore}` resolves blank on *every* response,
  always — not intermittently. Treat blank as **"no signal available,"
  not "failed check"**: don't force `review` on a blank score alone, or
  every response from a deployment that skipped this step gets flagged
  forever, silently, with no obvious cause. A present, parseable score
  is a real signal (a low value should still force review; note `"1"` is
  Qualtrics's own fail-open default when reCAPTCHA fails to *load* on an
  *enabled* survey, not proof of a verified human). A present but
  unparseable/malformed non-blank value is a genuine anomaly worth
  treating as review, unlike a clean blank.
- Missing keys, wrong JSON types, or an unsupported `contract_version` are
  structural failures -> 4xx (unlike a quality failure, which is always a
  normal tracked `review`, never an error response).
- Stop requiring client-computed `extra_signals.drip_score` /
  `extra_signals.bfi_answered` — those keys no longer exist in the
  request. Don't weaken the demographics contract; only personality
  changes.

**Server-side DRIP calculator**: load the vendored TSV once, validate it
(same rules as `drip_spec.py`: exactly 15 pairs, no reused items, strict
boolean parsing), verify its hash matches `drip_spec.canonical_spec_sha256()`'s
algorithm exactly (reproduce the same canonical bytes — field order,
separators, real JSON types all have to match bit-for-bit or the hash
comparison is meaningless). From the 60 raw `bfi_NN` values: count
`bfi_answered` (exact `"1"`-`"5"` match). For `drip_score`: if any item
needed by the 15 pairs is unanswered/malformed, `drip_score` is not
computable — return `null`/an explicit unavailable marker and force
`review`; never compute a partial sum over only the available pairs. A
non-DRIP item being unanswered can still leave `drip_score` computable
while `bfi_answered < 60` forces review anyway — these are independent
checks, not one combined pass/fail.

**Verdict**: `pass` requires `bfi_answered == 60` AND `drip_score`
computable AND `0 <= drip_score < drip_cutoff` AND
`attention_check_score == "1"` AND no `drip_spec_sha256` mismatch AND
(`recaptcha_score` is blank, **or** it's present and satisfies the
configured reCAPTCHA policy — blank never blocks `pass` on its own, only
a present-and-failing score does). Any failure of these is a normal
tracked `review`, never a 422 — reserve 4xx strictly for the structural
failures above.

**Privacy/governance**: this is the one substantive behavior change worth
flagging loudly. The old design sent only two derived numbers
(`drip_score`, `bfi_answered`) to `ase2-ai-mode`; this design sends all 60
raw personality item answers plus Prolific identifiers. Before deploying:
confirm ethics/IRB approval covers this, that participant disclosures
mention it if required, that a data-retention policy exists for raw
answers received this way (don't persist them by default beyond what the
computed signals/verdict need), and that request bodies are redacted from
application logs, reverse-proxy logs, error reporting, and tracing/APM —
not just from the primary datastore.

## 7. Live validation checklist

Structural tests (`python3 -m unittest discover tests`, `qsf_lint.py`)
catch generator bugs, not Qualtrics runtime behavior. Before treating this
as more than a generated draft:

- [ ] Import cleanly; confirm no generic import failure.
- [ ] Complete the survey twice with different, distinctive answer
      patterns (not the same value repeated for every item) and confirm
      two different responses' Web Service requests contain the correct,
      differing per-item values — not just that `bfi_01` and `bfi_60` are
      present (that alone wouldn't catch a systematic off-by-one across
      the middle 58 fields).
- [ ] Deliberately skip one item (BFI-2's `ForceResponse` is a soft
      prompt) — ideally one of the 15 DRIP-paired items — and confirm its
      `bfi_NN` field arrives as exactly `""`, not omitted, not a literal
      unsubstituted `${...}` template, not `null`.
- [ ] Confirm the Web Service actually fires synchronously (its response
      is what determines the redirect, not a race).
- [ ] Once the manual `Branch`/redirect nodes exist: fail the attention
      check and confirm routing goes to review; enter an inconsistent
      DRIP-pair pattern and confirm `drip_score` rises and routes to
      review past the configured cutoff even with a correct attention
      check; stop the Web Service endpoint (or point at an unreachable
      URL) and confirm the fail-closed defaults route to review, never to
      a stale/blank success.
- [ ] Hand-verify one reverse-keyed RPS item and the Risk Propensity
      total against `output/BFI-2_Full_RPS.qsf`'s score report, same
      spot-check method `.claude/skills/bfi2-qsf-splitter/SKILL.md`
      documents for BFI-2 items.
- [ ] Confirm `prolific_pid`/`prolific_study_id`/`prolific_session_id`
      actually populate from `PROLIFIC_PID`/`STUDY_ID`/`SESSION_ID` URL
      query parameters when the survey is loaded that way — not assumed
      from the Embedded Data defaults alone.
- [ ] Confirm every `ResponseMap` entry's destination field is actually
      populated (not blank) in a completed-response export — the
      key/value orientation bug (§3) silently produced blank fields with
      correctly-named columns, which looked superficially fine until the
      cell contents were actually checked.
- [ ] After manually enabling Bot Detection in the UI (not generated —
      see "Generated vs. still-manual" above): confirm
      `Q_RecaptchaScore`/`Q_RecaptchaStatus`/`Q_RecaptchaError`/
      `Q_BallotBoxStuffing`/`Q_PrivateBrowserDetected` all appear as
      columns in a completed-response export (this needs
      `IncludeSecurityFields` — `Q_RecaptchaScore` alone works as piped
      text without it, but the others, and `Q_RecaptchaScore` showing up
      *in the export*, do not).
